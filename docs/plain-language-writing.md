# 面向零基础的写作约定

这份教程的读者不需要先会编程。技术名称用于以后查阅，不应成为读懂当前段落的门槛。

1. **先解释正在解决什么问题。** 例如先说“材料太长，模型这一轮放不下”，再介绍上下文压缩；不要直接用“状态压缩契约”解释另一个陌生词。
2. **先给具体例子，再讲一般规律。** 可以沿同一张工单或一份手册展开，每个例子说明不同机制，不能把同一段模板贴到不同主题。
3. **一个句子尽量讲一件事。** 需要同时区分输入、输出、范围和限制时，拆开讲。技术术语第一次出现时，当场说明含义和用途。
4. **简化表达，保留关键区别。** 参数不是文本记录；上下文不是全部历史；工具返回不等于业务做完；缓存不等于训练；便宜调用不等于合格任务总成本低。类比后要交代不能直接对应的地方。
5. **深入来自因果和例外，不来自长词。** 解释为什么需要、怎样运作、何时有用、什么情况会失败。保留必要公式和字段名，但先说明它们表达的信息，再给数值例子。
6. **读完留下一句有内容的话。** `takeaway` 应总结这篇独有的核心，不能反复写“保留版本、检查效果”。`plain_intro` 应对应本篇问题，而不是所有文章通用的宣传语。

网页与Markdown共同采用：直接解释 → 具体例子 → 可选前置阅读 → 类比与图 → 分节讲机制 → 对比 → 一句话记住 → 误区和问答 → 来源。

表达修订和事实核验是两件事。改写不冒充重新实测工具，也不随意改变已经核对的版本说明、来源、限制和前置关系。新增内容依然需要适用的原始资料。
